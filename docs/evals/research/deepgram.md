# Deepgram on evaluating voice agents — research notes

Sources: deepgram.com blog/learn posts and developers.deepgram.com docs, fetched 2026-11-13.

## What they say

### Full-agent evaluation: score the whole call (VAQI)
- Deepgram's [Voice Agent Quality Index (VAQI)](https://deepgram.com/blog/voice-agent-api-generally-available) grades multi-turn conversations on three dimensions: **end-to-end latency** (response starts <1000 ms after the user stops speaking), **interruption rate** (agent starts talking too early — poor turn-ending detection), and **response coverage** (agent fails to respond at all — usually dropped/incomplete transcription of short utterances).
- Composite weighting: **40% interruptions, 40% response coverage, 20% latency** — conversational timing and completeness matter more than raw speed.
- Benchmark methodology: 121 identical conversations per provider, audio streamed in **50 ms increments to simulate real-time input**, default (untuned) agent settings, equivalent LLMs (GPT-4o variants) across providers, per-file normalization so outlier conversations don't skew scores.
- Their dedicated VAQI article URL now redirects to a generic [benchmarks page](https://deepgram.com/learn/voice-agent-quality-index); the methodology above comes from the Voice Agent API GA post. The benchmarks page FAQ adds target bands: keyword recall 80–90%, entity accuracy 70–90% — WER alone "treats every error as equal."

### Pre-production testing: scenario suites with written outcomes
- [Voice Agent Testing: Evaluate Before Taking Real Calls](https://deepgram.com/learn/voice-agent-testing-evaluate-before-real-calls) prescribes a ~9-scenario suite with written expected outcomes, re-run **after every prompt edit** (they cite research that identical prompt changes had inconsistent direction across model updates — "55% had no consistent direction"). Keep prompt versions + scorecards in source control.
- Each conversation passes/fails on **four measures**: task completion (binary), turns-to-resolution (count), escalation (reached a human when needed), and false statements (claims contradicting policy/DB — human- or LLM-judged; one cited LLM judge hit ~90% precision/recall vs human labels, but a human owns final authority).
- The nine scenarios: happy path; mid-sentence self-correction; **caller interruption** (barge-in + correct resume point); **3-second silence** (timeout/re-prompt); out-of-scope request (escalate, don't invent); background noise (endpointing); regional/non-native accent (names/alphanumerics); angry-but-polite caller (stressed prosody); wrong-number caller.
- Barge-in failure mode they call out: agent finishes its scripted line, then "replies to what the caller said before the interruption."
- Staging ladder: playground with uploaded clips (isolate model/endpointing) → one real call per scenario over production transport → production monitoring (latency per hop, sliced by language/transport, under concurrent load). First-week watchlist: transfer success, silence-triggered hangups, intents with no scorecard row; failed calls become new suite rows.

### Real vs synthetic test audio
- Same post: TTS test audio "defaults to a flat, even register, which is the easiest input your stack will ever get"; untuned *emotional* TTS runs ~25–35% higher WER than neutral baselines. Real callers add hesitations, overlaps, self-corrections, disfluencies, variable gaps — scripted clips have none unless deliberately added. **Recorded real calls with written outcomes are the deliverable.**
- [Speech recognition accuracy: production metrics](https://deepgram.com/blog/speech-recognition-accuracy-production-metrics): match microphones, environments, demographics, and the noisy:clean ratio of your production traffic; academic sets (LibriSpeech etc.) don't predict field accuracy. Sizing guidance: ≥10,000 words (~1 h) per condition for 95% confidence; ~5 h across ~2,000 files for broad coverage. Same API measured 92% (clean headset) / 78% (conference room) / 65% (mobile) — acoustic conditions, not the model, explained most variance. Use bootstrap resampling / sign tests to separate real differences from noise.

### STT metrics: WER variants and when they matter
- [WER/KER/KRR explainer](https://deepgram.com/learn/what-developers-need-to-know-about-wer-ker-and-krr) and the production-metrics post: **WER** = (S+D+I)/N is the baseline but equal-weights errors; **KER** (keyword error rate) and **KRR** (keyword recall rate) measure domain-critical terms — a system can have acceptable WER "yet still miss one-third of key terms." [Keyterm prompting](https://developers.deepgram.com/docs/keyterm) (Nova-3/Flux) exists to raise KRR. Also: CER for numbers/part codes, punctuation error rate (downstream intent/sentiment degrades 15–30% without boundaries), RTF <1.0, and a warning that STT **confidence scores are systematically overconfident** — don't use them as a quality signal.
- Normalization protocol before scoring (lowercase, strip punctuation, expand contractions, standardize numerals, drop fillers): inconsistent normalization alone shifts WER 2–5 points. [Benchmarking guide](https://deepgram.com/learn/speech-to-text-benchmarks): identical harness per vendor, standardized scoring lib (e.g. `jiwer`), log full JSON per file, slice results by acoustic condition rather than reporting one aggregate.
- Batch beats streaming by ~10–17 WER points (full context), so measure streaming accuracy on streaming output, not batch re-runs.

### Latency measurement methodology
- [Measuring STT latency](https://developers.deepgram.com/docs/measuring-streaming-latency) defines two distinct metrics: **transcript latency** = audio-cursor (seconds of audio sent) minus transcript-cursor (audio covered by latest **interim** result) — "use only interim transcripts; finals are delayed by endpoint detection"; and **end-of-turn latency** = wall-clock from true speech end (found via VAD on the source audio) to the EOT/final event. Don't trust Deepgram's own `start`/`duration` timestamps at ms precision. Targets: network 20–200 ms, transcription 150–300 ms, total transcript 200–500 ms, EOT detection 100–500 ms. Stream in 20–100 ms buffers.

### Turn-taking / endpointing evaluation
- [Flux launch post](https://deepgram.com/blog/introducing-flux-conversational-speech-recognition): end-of-turn detection is evaluated with **precision** (no premature cut-offs = no agent interruptions), **recall** (catches true turn ends), **F1**, plus latency distributions (median EOT <300 ms, ~p95 1.5 s) and a "fast-response rate" (% of detections <500 ms). The EOT confidence threshold is an explicit speed/accuracy dial (`eot_threshold`, default 0.7; "eager" 0.3–0.5 responds 150–250 ms earlier at the cost of 50–70% more LLM calls) — i.e., endpointing quality is a tunable precision/latency tradeoff, and they test it on deliberately hard audio: more noise, denser disfluencies, trickier pauses.

### Metrics to avoid
- [AI voice agents vs human agents](https://deepgram.com/learn/ai-voice-agents-vs-human-agents-metrics-comparison): legacy call-center metrics mislead — average handle time rewards fast wrong answers, raw containment counts silence as success, CSAT reflects routing. Instead: sample *contained* calls for quality, grade escalation timing (too early/too late), test STT on names/account numbers **against your own audio** before trusting vendor claims, and cluster failures by accent, intent, time of day. QA must specifically catch "confident wrongness."

## Applicability to our app

- **Add VAQI-style turn metrics off-line from Weave traces**: per turn, compute (a) interruption — agent audio started while caller was still speaking (we have both audio streams on the voice_turn span, so VAD over caller audio vs TTS start timestamp gives this), and (b) response coverage — caller turn with no agent response. Weight 40/40/20 with our existing voice-to-voice latency for a single per-session score. Pure post-hoc analysis, zero hot-path cost.
- **Our replay harness is exactly their recommended input**: real recorded caller audio, turn-by-turn, real-time pacing (their benchmark used 50 ms streaming increments; ours is real-time paced). Prefer replay over `e2e_check.py`'s synthesized turn for accuracy claims — flat TTS is "the easiest input your stack will ever get." Keep e2e_check as a plumbing smoke test only.
- **Extend `safety_check.py`'s grading to their four pass/fail measures**: task completion (did `book_engineer_visit` fire with correct args), turns-to-resolution (count), escalation correctness (booked vs invented a fix), false statements (LLM judge — we already have judge infra). These are cheap additions to the existing 16-scenario CI gate.
- **Add their missing scenario types** to the suite: barge-in with resume-point check (must answer the *interruption*, not the pre-interruption script — directly tests our VAD barge-in), 3-second silence (tests idle-timeout re-prompt vs hang-up), background noise, accented speech, angry caller (assert our `vocal_frustrated` acoustic judge fires), wrong-number graceful exit.
- **Fix the latency-metric conflation**: our `stt_final_ms` mixes transcription latency with endpointing delay, which Deepgram explicitly warns against. Log interim-based transcript latency (audio cursor − interim cursor) separately from EOT delay; both can be computed from data we already have, outside the hot path. Report p50/p95 across sessions, not means.
- **Track keyword recall, not just transcripts looking plausible**: build a keyterm list (appliance brands, model/part numbers, "engineer visit") and score KRR/CER on replayed sessions; consider Nova-3 keyterm prompting if recall is low. Use `jiwer` with their normalization protocol so numbers are comparable run-to-run.
- **Re-run the suite on every prompt edit** (already our CI pattern) and store scorecards per prompt version; their cited result — prompt changes flip sign across model updates — justifies keeping this as a hard gate.
- **Don't use Deepgram confidence scores** as a transcript-quality signal in any judge/monitor — systematically overconfident per their own guidance.
- **Test-set realism over size**: their 10k-words-per-condition bar is overkill for a teaching repo, but the principle applies — replay sessions should span clean/noisy/accented callers in roughly the mix we expect, and failures found in live sessions should become new replay fixtures.
