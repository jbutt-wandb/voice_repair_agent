# W&B Weave Evaluations — framework research

Researched 2026-11-13 against docs.coreweave.com/weave (identical content served at docs.wandb.ai/weave).
Project SDK: weave **0.53.12** (verified locally: exports `Evaluation`, `EvaluationLogger`, `Dataset`, `Scorer`, `Audio`, `SavedView`, `Monitor`, `Leaderboard` via `weave.flow.leaderboard`).

## What they say

### weave.Evaluation — the declarative API
- Shape: `weave.Evaluation(dataset=..., scorers=[...], trials=N, preprocess_model_input=fn, evaluation_name=...)`; run with `asyncio.run(evaluation.evaluate(model_or_op))` ([evaluations](https://docs.coreweave.com/weave/guides/core-types/evaluations)). Verified field list on 0.53.12: `name, description, dataset, scorers, preprocess_model_input, trials, metadata, evaluation_name`.
- The "model" is either a `weave.Model` subclass with a `@weave.op predict()` method or any plain `@weave.op` function ([evaluations](https://docs.coreweave.com/weave/guides/core-types/evaluations)).
- `trials=N` runs each dataset example N times; `preprocess_model_input` transforms a row before it reaches the model ([evaluations](https://docs.coreweave.com/weave/guides/core-types/evaluations)).
- Examples run in parallel, `WEAVE_PARALLELISM` env var (default 20; set 1 for sequential) controls concurrency ([env-vars](https://docs.wandb.ai/weave/guides/core-types/env-vars)).

### Scorers — how they receive inputs/outputs
- Function scorers: `@weave.op` functions returning a dict. The `output` parameter receives the model output; **any other parameter name is auto-matched to a dataset column of the same name** ([scorers](https://docs.coreweave.com/weave/guides/evaluation/scorers)).
- Class scorers: subclass `weave.Scorer`, implement `@weave.op score(...)` returning a dict; `column_map={scorer_arg: dataset_column}` handles name mismatches ([scorers](https://docs.coreweave.com/weave/guides/evaluation/scorers)).
- Async is first-class: scorers and model ops can be `async def`; scorers "run asynchronously after the main operation completes" ([scorers](https://docs.coreweave.com/weave/guides/evaluation/scorers)).
- Aggregation: `auto_summarize` averages/aggregates per return type; override `summarize(score_rows) -> dict` for custom rollups ([scorers](https://docs.coreweave.com/weave/guides/evaluation/scorers)).
- Built-ins (`pip install weave[scorers]`, Python only): HallucinationFree, Summarization, OpenAIModeration, EmbeddingSimilarity, ValidJSON/XML, Pydantic, RAGAS ContextEntityRecall/ContextRelevancy — LLM-judge ones call out via litellm/OpenAI **from your process** ([builtin scorers](https://docs.coreweave.com/weave/guides/evaluation/builtin_scorers)). Nothing audio-specific among them.

### Client-side vs server-side execution (key distinction)
- Evaluations and their scorers are ordinary Python running wherever you call `evaluate()` — i.e., client-side; results are logged to Weave. The docs' server-side alternative, a "remote scorer," is explicitly "a scorer that runs on your infrastructure instead of inside W&B Weave" and "runs only through a monitor" — confirming Monitors are the server-side path and evals are not ([remote scorers](https://docs.wandb.ai/weave/guides/evaluation/remote-scorers)).
- Monitors: server-side LLM judges that passively sample production traces; the judge is sent a text prompt built from the turn (optionally tool calls); no media/audio input capability is documented ([custom monitors](https://docs.coreweave.com/weave/guides/evaluation/custom-monitors)). **Project-verified fact: Weave Monitors cannot read `weave.Audio` inputs** — consistent with the docs describing text-only judge context. Client-side eval scorers do not share this limit: your scorer code can open the audio bytes itself.
- Guardrails are the other client-side hook: `call.apply_scorer(scorer)` runs a scorer inline on a live call, "in real time before outputs reach users" — i.e., on the hot path ([guardrails](https://docs.coreweave.com/weave/guides/evaluation/guardrails_and_monitors)).

### EvaluationLogger — the imperative API
- For systems that aren't a callable function (e.g., a live WebSocket session): `EvaluationLogger(model="...", dataset="...")` where model/dataset are strings **or dicts with metadata**; then per example `pred = log_prediction(inputs=..., output=...)`, `pred.log_score(scorer="name", score=val)`, `pred.finish()`, and finally `eval_logger.log_summary({...})` for eval-level aggregates ([evaluation_logger](https://docs.coreweave.com/weave/guides/evaluation/evaluation_logger)).
- No predefined Dataset/Scorer objects needed; you decide what counts as an example and a score. Context-manager form (`with log_prediction(...) as pred:`) and one-shot `log_example(inputs, output, scores)` exist in Python ([evaluation_logger](https://docs.coreweave.com/weave/guides/evaluation/evaluation_logger)).
- **Rich media works in logged predictions**: docs show PIL images as inputs and audio objects as outputs of `log_prediction` ([evaluation_logger](https://docs.coreweave.com/weave/guides/evaluation/evaluation_logger)).
- Initialize the logger before LLM calls so token/cost usage is captured; after `finish()` no more scores can be added ([evaluation_logger](https://docs.coreweave.com/weave/guides/evaluation/evaluation_logger)).

### Datasets and media
- `weave.Dataset(name=..., rows=[{...}])`; publish with `weave.publish(dataset)`; new versions on edit; rows can come from traced calls or DataFrames; UI row editing supported ([datasets](https://docs.coreweave.com/weave/guides/core-types/datasets)).
- The Dataset page is silent on media in rows and on size limits ([datasets](https://docs.coreweave.com/weave/guides/core-types/datasets)). The media guide covers audio in trace I/O — mp3/wav/flac/ogg/m4a, `wave.Wave_read` return values, and the `Annotated[bytes, Content]` pattern — and says audio renders playable in the trace UI, but doesn't address dataset rows ([media](https://docs.coreweave.com/weave/guides/core-types/media)). `weave.Audio` exists as a class in SDK 0.53.12 (and is already used in this repo's `server/weave_trace.py`), so passing it through eval inputs/outputs serializes like any traced media; treat media-in-`Dataset`-rows as unverified until tested.
- No documented per-payload size limit; billing docs only define "ingested bytes" (free academic tier example: 25 GB/mo ingestion) ([ingestion FAQ](https://docs.wandb.ai/support/weave/articles/how-is-weave-data-ingestion-calculated)). Large non-dict outputs may be truncated unless returned as dicts/known types.
- The [audio cookbook](https://docs.coreweave.com/weave/reference/gen_notebooks/audio_with_weave/) traces OpenAI Realtime API voice conversations (per-event `@weave.op`s buffering audio deltas into WAV via `io.BytesIO`, returning `wave.open(...)` handles) — a tracing demo; it contains **no audio evaluation/scorer example**. No audio-eval cookbook was found anywhere in docs or the wandb/weave repo.

### Results UI: comparison, leaderboards, saved views
- Each eval gets a page with per-example rows; "Compare" opens a comparison view: Summary tab (radar chart + per-metric bar/coverage charts, baseline deltas as colored badges) and Dataset results tab (per-example table: input alongside each eval's output and scores; click a row for side-by-side detail; two scatter plots for divergence-hunting when comparing exactly 2 evals; brush to filter) ([compare_evals](https://docs.coreweave.com/weave/guides/evaluation/compare_evals)). Leftmost eval is baseline by default; 2+ evals comparable; Weave warns on dataset/scorer inconsistencies between runs.
- Leaderboards rank models across evaluations: `leaderboard.Leaderboard(columns=[LeaderboardColumn(evaluation_object_ref=..., scorer_name=..., summary_metric_path="mean")])`, published via `weave.publish` or built in the UI ([leaderboards](https://docs.coreweave.com/weave/guides/core-types/leaderboards)).
- Saved views persist filters/sorts/columns for Traces **and Evals** tables, via UI or `weave.SavedView()` in Python ([saved views](https://docs.coreweave.com/weave/guides/tools/saved-views)).

## Applicability to our app

- **EvaluationLogger is the right primitive for pipeline-level evals.** Our "model" is a live WebSocket session (replay harness feeding recorded caller audio through the real mic path), not a function `weave.Evaluation` can call. Pattern: one `EvaluationLogger` per replay run, one `log_prediction` per voice turn (inputs = caller audio + transcript, output = agent transcript + TTS audio), `log_score` for each judge, `log_summary` with session-level metrics (latency percentiles, booking success).
- **weave.Evaluation fits the text-level layer.** `scripts/safety_check.py`'s 16 scripted conversations map cleanly: `Dataset` rows = scripted conversations + expectations, model = an op wrapping the LLM/tool loop (no STT/TTS), scorers = the existing LLM judge split into named `@weave.op` scorers. `trials=N` gives repeat-sampling for flaky judge/LLM nondeterminism; results land in the comparison UI instead of pass/fail stdout.
- **Audio scoring must be client-side — and can be.** Confirmed: eval scorers run in our process, so the acoustic judge (gpt-audio-mini forced tool call) can be reused verbatim as a scorer that receives `weave.Audio`/bytes. This sidesteps the project-verified Monitor limitation (server-side judges are text-only).
- **Latency as a scorer, not just a log.** Per-turn latency JSON (stt_final_ms, llm_ttft_ms, tts_ttfb_ms, voice-to-voice) can be logged via `log_score`/`log_summary`, giving regression comparison across runs in the eval UI — enforcing the "never regress voice-to-voice latency" rule as a gated metric.
- **Zero hot-path risk.** Evals run offline against the replay harness or scripted text runs; nothing executes inside the live call. Avoid `call.apply_scorer` guardrails — they are explicitly in-band.
- **Media in eval tables**: playable audio in prediction inputs/outputs is documented for EvaluationLogger; audio inside `weave.Dataset` rows is undocumented — before building the golden dataset, run a 2-row smoke test; fallback is storing audio file refs/paths in rows and loading in `preprocess_model_input`.
- **Throughput/limits**: set `WEAVE_PARALLELISM=1` (or low) for replay evals — real-time-paced WebSocket sessions shouldn't run 20-wide against the dev server. No hard payload cap documented, but audio counts against ingestion quota; our ~16 kHz mono turns are small (~32 KB/s).
- **UI wiring**: publish a Leaderboard over (safety score, acoustic-frustration rate, p50 voice-to-voice) and a SavedView on the Evals tab filtered to CI runs; use compare-evals scatter plots to find turns where a model change moved latency or judge scores.
- **Version note**: all APIs above (`Evaluation.trials`, `EvaluationLogger`, `weave.Audio`, `SavedView`) verified present in the pinned SDK 0.53.12.
